# Restaurant POS Commercial V3 Requirements

## 目标

把现有餐厅点餐系统整理成一套稳定、可维护、可长期商用的连锁餐厅系统。

原则：
- 保留现有业务成果，不从空白项目重做。
- 新建 V3 商用版架构，逐步迁移和重构核心模块。
- 先保证数据安全和多设备一致性，再优化界面和扩展功能。
- 所有关键业务规则记录在本文档，避免后期靠记忆修改。

## 当前系统定位

现有系统已经包含：
- POS 收银
- 服务生点餐
- 厨房显示
- 桌台管理
- 库存管理
- 菜品管理
- 采购管理
- 财务报表
- 员工管理
- 店长管理
- 分店管理
- 权限管理
- Firebase Hosting / Firestore 云端同步
- 本地缓存和断网可用雏形

结论：
- 业务方向正确。
- 功能覆盖面接近真实餐厅运营。
- 目前还不适合直接作为完全稳定的商用系统。
- 最合适路线是基于当前干净仓库做 V3 商用版重构。

## 核心商用要求

### 1. 分店隔离

要求：
- 每个分店的数据必须通过 `storeId` 隔离。
- 店长、收银、服务生、厨师只能访问所属分店数据。
- 老板/admin 可以查看所有分店数据。
- 分店之间订单、桌台、库存、员工、财务不能互相污染。

需要覆盖的数据：
- 桌台
- 订单
- 菜品
- 库存
- 采购
- 日常开支
- 员工
- 班次
- 顾客
- 权限
- 操作日志

### 2. 多设备实时同步

真实场景：
- 同一分店可能有多台电脑、POS 终端、服务生设备、厨房屏同时使用。
- A 设备下单后，B 设备必须实时看到桌台状态和订单。
- 不能出现 A/B 两台设备各自为政。
- 不能出现旧数据覆盖新数据。

要求：
- Firestore 为云端权威数据源。
- 本地缓存只做离线读取和临时队列。
- 所有云端数据必须有版本字段或更新时间字段。
- 同一条数据更新时，只允许新版本覆盖旧版本。
- 核心操作必须幂等，重复提交不能重复扣库存或重复生成订单。

### 3. 断网可用

要求：
- 断网时 POS 可以继续点餐、下单、收款。
- 断网期间操作进入本地离线队列。
- 恢复网络后自动同步到 Firestore。
- 同步失败时必须提示，并保留待同步记录。
- 不能因为刷新页面丢失未同步数据。

风险点：
- 断网期间多设备同时修改同一桌或同一库存，恢复网络后需要冲突处理。

### 4. 订单流程

堂食标准流程：
1. 选择桌台。
2. 添加菜品。
3. 确认下单。
4. 订单发送到厨房。
5. 桌台变为占用状态。
6. 右侧订单列表显示当前当天订单。
7. 支付后桌台进入待清台状态。
8. 清台后订单完成，桌台恢复空闲。

订单状态建议：
- `draft`: 草稿
- `confirmed`: 已下单/已发送厨房
- `preparing`: 制作中
- `served`: 已上菜/已交付
- `paid`: 已支付待清台
- `completed`: 已完成
- `cancelled`: 已取消

注意：
- 历史订单页面显示历史订单。
- POS 右侧订单区只显示当天订单，不混入历史订单。
- 今天/日期/状态/类型必须支持过滤。
- 历史订单列表按最新订单在前排序。

### 5. 桌台状态

要求：
- 空闲：绿色。
- 已下单/制作中：红色。
- 已支付待清台：橙色，并显示清扫标识。
- 清台完成：恢复绿色。

同步要求：
- POS 桌台和服务生桌台必须使用同一份桌台数据。
- 不能 POS 一套桌台，服务生一套桌台。
- 添加/删除桌台不能导致旧桌台批量覆盖回来。

### 6. 取消和修改授权

要求：
- 已发送厨房的菜品，修改数量或取消必须授权。
- 取消整单必须授权。
- 授权密码可由老板/店长设置。
- 当前临时规则：
  - 老板密码：`admin123`
  - 店长密码：`123456`
- 授权弹窗必须可以正常输入密码和原因。
- 授权操作必须记录日志：
  - 操作类型
  - 操作人
  - 授权人
  - 原因
  - 时间
  - 涉及订单/菜品

### 7. 支付和清台

要求：
- 订单支付后必须保存支付状态。
- 支付后桌台变橙色待清台。
- 顾客可以先支付后继续用餐，中途继续加菜。
- 支付不代表订单最终完成。
- 点击清台后订单完成，桌台恢复空闲。
- 支付记录必须写入财务数据。
- 支持现金、刷卡、混合支付。
- 后续可扩展美元/科多巴汇率。

### 8. 库存扣减

酒水/饮料真实业务规则：
- 总库存 = 仓库 + 冰箱。
- 销售优先扣减冰箱数量。
- 冰箱不足时，再扣减仓库数量。
- 仓库可以调拨到冰箱。
- 销售后冰箱数量会变化，总库存也会变化。

要求：
- POS 销售不在确认下单时扣库存。
- POS 支付也不直接扣库存，因为存在先支付后用餐、中途继续加菜的场景。
- 库存统一在订单完成时一次性扣减，也就是清台完成并将订单状态改为 `completed` 时扣减。
- 订单完成扣库存必须覆盖整单最终菜品数量，包含中途加菜和已授权减少的数量。
- 库存扣减必须使用事务或可回滚机制。
- 不能重复扣减。
- 已完成订单必须标记 `stockDeducted = true` 和 `stockDeductionOperationId`，避免刷新、重试、多设备同步时重复扣库存。
- 未完成订单取消时不需要恢复库存，因为库存尚未扣减。
- 已完成订单后如果需要作废或退款，不能直接删除订单或反向改数量，必须走冲正/退货库存流水。
- 冰箱盘点、仓库盘点、库存管理必须显示同一套库存数据。
- A 设备修改库存，B 设备必须实时更新。

### 9. 菜品和菜单

要求：
- 菜品管理中新增/编辑/删除菜品必须保存到云端。
- 多设备菜品列表数量必须一致。
- POS、服务生端、厨房端都读取同一份菜品数据。
- 菜品可以关联库存：
  - 直接扣库存商品
  - 配方扣库存商品
  - 不扣库存商品
- 菜品需要支持图片。
- 菜品图片不能直接使用原始大图加载到浏览器。
- 上传或导入图片时必须生成压缩版本，方便 POS、服务生端和菜单页快速打开。

菜品图片建议规则：
- 原图：仅用于备份或后续重新生成压缩图，不在普通页面直接加载。
- 缩略图：用于 POS 菜品网格和快速浏览，建议宽度 160-240px。
- 中图：用于菜品详情、菜单管理预览，建议宽度 600-900px。
- 图片格式优先使用 WebP；不支持时可回退 JPEG。
- 图片质量建议 70%-80%，在清晰和体积之间平衡。
- 图片文件名和路径要稳定，避免菜品编辑后旧图片残留无法清理。
- 菜品数据只保存图片 URL 和元数据，不把 base64 大图直接写入 Firestore。
- 图片应存放在 Firebase Storage 或静态资源目录，Firestore 只保存引用。
- POS 首屏不能一次性加载所有大图，需要懒加载。
- 图片加载失败时显示默认占位图，不能影响点餐。

菜品图片字段建议：
- `imageThumbUrl`
- `imageMediumUrl`
- `imageOriginalUrl`
- `imageUpdatedAt`
- `imageStoragePath`
- `imageHash`

### 10. 财务

要求：
- 采购支出必须进入采购支出分类。
- 日常开支必须进入日常开支分类。
- 采购支出刷新后不能消失。
- 财务报表要能按日期、分店、类别统计。
- 收款、退款、取消、采购、日常开支必须有明细。

### 11. 员工和权限

固定角色：
- 店长
- 收银
- 服务生
- 厨师

要求：
- 角色固定，不重复生成。
- 每个角色的权限可以自由配置。
- 员工新增后刷新仍然存在。
- 员工账号和分店绑定。
- 权限不能只靠前端隐藏按钮，关键操作需要数据层规则保护。

### 12. 时间和时区

使用地：
- Nicaragua / America/Managua

要求：
- 前端显示使用尼加拉瓜本地时间。
- 云端保存使用统一时间格式。
- 日期过滤必须按尼加拉瓜当地日期判断。
- 今天、昨天、历史订单不能因时区错误混乱。

### 13. 数据安全

要求：
- Firestore 数据不能因为代码更新而丢失。
- 数据结构升级必须有迁移脚本。
- 重要数据必须支持导出和恢复。
- 后续需要定期备份策略。

重要数据：
- 订单
- 支付
- 库存
- 采购
- 开支
- 员工工资/借款
- 分店
- 权限
- 顾客
- 操作日志

### 14. 多语言界面

使用场景：
- 系统在尼加拉瓜使用。
- 管理人员需要中文界面。
- 当地员工可能需要西班牙语界面。

要求：
- 系统必须支持中文和西班牙语。
- 用户可以切换界面语言。
- 每个账号可以保存自己的默认语言。
- 语言切换不能影响数据内容和业务逻辑。
- POS、服务生端、厨房端、库存、财务、员工、权限都要逐步支持双语。
- 菜品、库存物品、供应商、备注等业务数据不需要双语字段，直接按实际经营环境录入西班牙语。
- 系统只翻译固定界面文案、按钮、菜单、状态、提示、弹窗。

界面文案字段建议：
- 中文：`zh-CN`
- 西班牙语：`es-NI`

业务数据语言规则：
- 菜品名称：直接使用西语字段 `name`。
- 菜品描述：直接使用西语字段 `description`。
- 菜品分类：直接使用西语字段 `categoryName` 或分类 ID。
- 库存物品名称：直接使用西语字段 `name`.
- 供应商、采购备注、库存备注：按实际需要录入西语。
- 不为业务数据额外建立 `nameZh/nameEs` 这类双语字段，避免维护复杂度过高。

语言策略：
- 默认语言可按账号设置。
- 老板/admin 默认中文。
- 店长可选中文或西语。
- 收银、服务生、厨师可选中文或西语。
- 如果某条文案缺少西语，先回退到中文。
- 业务数据按录入内容原样显示，不做自动翻译。

技术要求：
- 不允许在页面里继续散落硬编码文案。
- 建立统一 i18n 文案文件。
- 常用按钮、状态、错误提示、弹窗都走统一翻译函数。
- 订单状态、支付状态、库存状态必须可翻译。

### 15. 老板手机端和后期 APP

使用场景：
- 老板不一定在店里，需要手机远程查看所有分店运营数据。
- 手机端主要用于查看、预警和审批，不作为高频点餐端。
- 后期可以在手机网页版稳定后封装成 APP。

第一阶段建议：
- 先做手机网页版 / PWA，不急着做原生 APP。
- 路由建议：`/owner-mobile`。
- 可添加到手机桌面，像 APP 一样打开。
- 与 POS、库存、财务共用同一套 Firebase 数据。

老板手机端功能：
- 查看所有分店今日营业额。
- 查看现金、刷卡、总收入。
- 查看订单数量、客单价、取消订单数量。
- 查看各分店当前桌台状态。
- 查看未完成订单、待清台订单、异常订单。
- 查看采购支出、日常开支、净收入。
- 查看库存预警和缺货商品。
- 查看员工考勤和工资概览。
- 按今天、昨天、本周、本月、自定义日期筛选。
- 多分店对比。
- 异常提醒，例如库存低、取消订单多、支出异常。

权限原则：
- 老板/admin 可以跨分店查看。
- 手机端默认以查看为主。
- 危险操作需要二次确认和操作日志。
- 手机端不建议直接删除订单、改库存、改财务。
- 可考虑支持远程审批，例如大额支出审批、取消订单授权、采购审批。

后期 APP 路线：
- 先完成 PWA。
- PWA 稳定后再用 Capacitor / React Native / Flutter 封装。
- APP 不另建一套数据，继续使用 Firebase。
- 后期可增加推送通知：
  - 每日营业总结
  - 库存低提醒
  - 分店收银异常
  - 店长取消订单提醒
  - 采购支出审批提醒

## 实施顺序

### Phase 1: 设计和防护

目标：
- 明确数据结构。
- 明确同步规则。
- 建立测试环境和备份策略。

任务：
- 整理 Firestore 数据模型。
- 整理订单/桌台/库存状态机。
- 确认权限矩阵。
- 确认中西双语字段和界面翻译规则。
- 确认菜品图片压缩、存储和懒加载方案。
- 增加数据导出和备份入口。

### Phase 2: POS 核心稳定

目标：
- 多设备 POS 不乱。
- 桌台、订单、支付、清台稳定。

任务：
- 重构 POS 数据流。
- 统一桌台数据源。
- 统一当天订单列表。
- 修复支付、清台、取消、修改数量完整闭环。

### Phase 3: 库存稳定

目标：
- 仓库/冰箱/总库存准确。
- POS 销售扣减准确。

任务：
- 统一库存模型。
- 实现冰箱优先扣减。
- 实现仓库调拨到冰箱。
- 实现库存流水。
- 实现盘点差异记录。

### Phase 4: 财务和报表

目标：
- 收入、采购、开支、报表可追溯。

任务：
- 统一采购支出和日常开支。
- 支付自动进入收入。
- 按分店/日期/分类统计。

### Phase 5: 员工和权限

目标：
- 账号、角色、权限稳定。

任务：
- 固定四个角色。
- 权限矩阵可配置。
- 员工新增保存云端。
- Firestore Rules 约束核心数据访问。

### Phase 6: 商用测试和上线

目标：
- 真实餐厅场景压力测试。

任务：
- 两台电脑同步测试。
- 服务生端和 POS 同步测试。
- 厨房端同步测试。
- 断网下单和恢复同步测试。
- 数据备份和恢复测试。

## 未确认问题

以下规则需要用户确认：

1. 取消已支付订单是否允许？如果允许，库存和财务如何回滚？
2. 已发送厨房的菜品减少数量时，厨房端是否要显示取消/减少提醒？
3. 库存扣减时机已确认：订单完成时一次性扣，支付不扣，下单不扣。
4. 菜品配方扣库存是否需要支持半成品？
5. 员工工资、借款、考勤是否必须进入财务报表？
6. 老板是否需要手机端查看所有分店数据？
7. 是否需要打印小票、厨房单、交班单？
8. 是否需要客户积分和会员价？
9. 是否需要日结锁账，防止历史订单被修改？
10. 菜品原图是否需要长期保留，还是只保留压缩图？
11. 菜品图片是由后台上传，还是也允许 POS/手机端拍照上传？
