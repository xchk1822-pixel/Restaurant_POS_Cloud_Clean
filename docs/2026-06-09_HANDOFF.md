## Firestore Usage Decision

Today Firestore exceeded quota. The likely contributors are broad realtime subscriptions and repeated document reads from multiple devices.

Decision made:

- POS active orders must stay realtime.
- Inventory item and category management should not keep long-running realtime listeners.
- Inventory should use:
  - load on page open,
  - immediate local update,
  - write to Firestore on save,
  - manual refresh/re-enter page on another device.

Current code state:

- Removed global realtime subscription for `inventory_items` in `client/src/contexts/AppContext.tsx`.
- Replaced `inventory_categories` realtime subscription in `client/src/pages/Inventory/Inventory.tsx` with one-time `smartGetDocuments`.
- Kept realtime `pos_orders` subscription active for multi-device POS operation.

## Firestore Optimization Next Steps

Recommended next work:

1. Audit every `smartSubscribeToCollection(...)` call.
2. Split collections into policies:
   - realtime: `pos_orders`, `pos_tables`, kitchen-needed active order data.
   - one-time load: `inventory_items`, `inventory_categories`, `employees`, `expenses`, `purchase_orders`, `suppliers`.
   - admin-only one-time load: stores, users, roles.
3. Add an explicit refresh button to inventory screens.
4. Add a visible "last synced" time for inventory pages.
5. Add a Firestore usage guard in development/testing:
   - warn when a page opens many listeners,
   - log collection read/listener count,
   - avoid duplicate listeners for the same collection.
6. Consider paginating or lazy-loading large lists if Firestore data continues growing.
