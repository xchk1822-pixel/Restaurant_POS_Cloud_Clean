# POS Multi-Terminal Order Sync Guard - 2026-06-26

## Problem

The owner reported that POS order `0626031` and some occasional orders did not stay synchronized between two terminals. Newer orders could sync, but one terminal could keep showing an older paid/served state after another terminal completed or cancelled an order. The owner also confirmed the order number rule must stay as date plus sequence.

## Root Causes Fixed

1. POS incremental order publishing treated every resolved `smartUpdateDocument` call as cloud success. When weak network fallback returned a local pending write, POS could still mark the order signature as published and clear its pending retry marker.
2. POS had two separate effects deriving table status from orders. They could both update the same table state and contribute to flicker or competing state changes.
3. Kitchen display could write stale local order data back to `pos_orders` and regress a terminal POS order from `completed` or `cancelled` back to kitchen states such as `served` or `preparing`.
4. Waiter add-on flow kept a previously paid order as `paid` after adding more items, instead of recalculating `paid / partial / unpaid` from the settled amount and new total.
5. POS order numbers were generated by scanning the local terminal's visible orders, which is not safe for multiple terminals.

## Fix

- `client/src/pages/POS/POS.tsx`
  - Incremental publisher now awaits `smartUpdateDocument` and keeps pending retry state when the result is pending or failed.
  - Removed the duplicate table-status effect and left a single `reconcileTableStatusFromOrders` path.
  - Payment confirm button is disabled while payment is processing and shows `Procesando...`.
  - All new order-number calls now await `smartGenerateDailyOrderNumber`.

- `client/src/services/smartSyncService.ts`
  - Added `smartGenerateDailyOrderNumber(date)`.
  - Online path uses a Firestore transaction on `stores/{storeId}/order_counters/{yyyy-mm-dd}`.
  - Offline or weak-network fallback uses a store-scoped local daily counter so POS remains usable.

- `firestore.rules`
  - Added read/write rules for `stores/{storeId}/order_counters/{counterId}`.

- `client/src/pages/POS/KitchenDisplay.tsx`
  - Added terminal-order guard. Kitchen cannot overwrite POS orders already `completed` or `cancelled`.

- `client/src/pages/WaiterInterface/WaiterInterface.tsx`
  - Existing-order add-on flow recalculates payment status using settled amount versus new total.

- `client/src/utils/dataSafety.test.ts`
  - Added regression guards for pending publisher behavior, kitchen terminal guard, waiter add-on payment status, cloud daily order counters, and single table-status reconciliation.
